GastroClinic27: Technical Interview Preparation

Project-specific questions, concise model answers, and concepts to revise.

30-second introduction: GastroClinic27 is a responsive, frontend-first healthcare website for a five-location gastro clinic network. It uses React and Vite for the application, React Router for navigation, Tailwind CSS for the design system, Framer Motion for interaction, Web3Forms for form delivery, and OpenRouter for a tightly scoped AI clinic assistant.

1. Architecture and project design

Architecture1. What is the overall architecture of GastroClinic27?

It is a static React single-page application. Vite builds the source into deployable static assets; React Router renders the correct page in the browser; shared components wrap each route. External services handle form delivery and AI chat, so there is no custom application backend or database.

Concept: SPA, client-side routing, static hosting, third-party API integration.

2. Why did you choose Vite instead of Create React App?

Vite gives a faster development server through native ES modules and a leaner production build pipeline. It is the current lightweight choice for a client-side React application and is simpler to configure for this project.

Concept: Bundlers transform modules, optimize assets, and create production bundles. Vite uses Rollup for the production build.

3. How are the pages and routes organized?

Each screen lives under src/pages. App.jsx defines routes such as /services, /clinics, and /appointment. It also has a wildcard route for a 404 state. Shared UI such as Navbar, Footer, WhatsApp, and chat is mounted once in the app shell.

Concept: Separation of concerns and reusable layout composition.

4. Why centralize content in src/data/index.js?

Clinic details, schedules, services, FAQs, testimonials, and time slots are reused in more than one view. Centralizing them prevents duplication and reduces the chance of mismatched content. Later, that module could be replaced by a CMS or API with minimal component changes.

Concept: Single source of truth and data-driven rendering.

5. How would you scale this project if content changes frequently?

I would move the data layer to a headless CMS or secured API. The UI would continue to map over the same logical objects, while authorized staff could update clinic hours and services without a code deployment. I would add caching, validation, and fallbacks for unavailable content.

2. React and frontend concepts

React6. Explain state management in this application.

The scope is small, so component-level state with useState is sufficient. Forms hold their field values, errors, loading state, and success state locally. The chat component stores the open state, messages, input, and loading state. No global store is necessary yet.

Concept: Use local state first; introduce Context, Zustand, Redux, or server-state tools only when state must be shared widely or becomes complex.

7. How is dark mode implemented?

The reusable useDarkMode hook reads a saved localStorage preference, otherwise defaults to the OS colour preference. It adds or removes Tailwind's dark class on the document root and persists changes to local storage.

Concept: Custom hooks package reusable stateful behaviour; Tailwind class-based dark mode applies conditional styles.

8. What are React effects used for here?

Effects update the document title on navigation, scroll users to the top or a hash target, listen for system theme changes, manage the navigation scroll style, run chat intro timers, focus the chat input, and scroll the chat transcript to the latest message.

Concept: useEffect synchronizes React with external browser systems. Timers and event listeners require cleanup to avoid leaks.

9. How does the appointment page preselect a clinic?

It reads the clinic query parameter using React Router's useSearchParams. A clinic card can therefore link to a URL such as /appointment?clinic=3, and the form initializes with that clinic selected.

Concept: URL state makes a UI state linkable, shareable, and bookmarkable.

10. How do you avoid duplicated markup in the UI?

Repeated sections are rendered by mapping over structured data, and global elements are reusable components. Tailwind component classes such as btn-primary, card, and input-field also prevent visual styles from being repeated everywhere.

3. Forms, validation, and integrations

Forms11. Walk through the appointment form validation.

The form checks required fields, a 10-digit Indian mobile pattern, age from 1 to 120, gender, clinic, date, and time. It also compares the selected date's weekday with the chosen clinic's permitted operating days. Changing a clinic resets the selected time because time slots are clinic-specific.

Concept: Client validation improves UX but must be duplicated on the server for security and data integrity.

12. How are available appointment slots determined?

The selected clinic ID indexes clinicTimeSlots. This prevents users from selecting a time outside that clinic's advertised OPD hours. It is a schedule rule, not real-time capacity management.

Concept: Derived state should be calculated from source data instead of stored separately.

13. How are forms submitted without a backend?

The app sends a JSON POST request to the Web3Forms endpoint. On a successful response it updates the UI with a confirmation; on failure it shows a useful error and retains loading state correctly in a finally block.

Concept: Async/await, HTTP POST, loading/error/success states, and graceful failure handling.

14. What are the limitations of the current booking implementation?

It sends an appointment request but does not reserve a slot, prevent duplicates, maintain staff calendars, or store first-party records. A production booking platform should have an authenticated backend, database transaction or slot-locking policy, notifications, and staff confirmation workflow.

15. How would you protect forms from spam?

I would add a CAPTCHA or honeypot, backend rate limiting, server-side schema validation, IP/device abuse monitoring, and rate limits per endpoint. Client-side validation alone is bypassable because requests can be made outside the browser UI.

4. AI assistant and security

AI16. How does Dr. Vayu work?

The widget maintains a local conversation array, adds a system prompt that limits its scope, and calls OpenRouter's chat-completions API. The response is appended to the UI, and detected URLs are rendered as safe external appointment links.

Concept: Prompt engineering shapes model behaviour but cannot replace enforcement and validation.

17. How is medical safety addressed?

The system prompt restricts the chatbot to clinic timing, phone, service, and basic-awareness questions. It directs symptom and medical queries to a real doctor and disallows diagnoses, dosages, procedures, and treatment comparisons. The website also includes medical disclaimer pages.

18. What is the biggest security concern in the AI implementation?

The OpenRouter key is read from a Vite environment variable in the browser. Variables prefixed with VITE_ are embedded into client code, so they are not secrets. The API request should move to a backend or serverless proxy, where the key, rate limits, validation, moderation, and logging can be controlled.

Concept: Never expose privileged credentials in frontend bundles. Environment variables are not automatically secret.

19. How would you mitigate prompt injection?

I would not rely on the prompt alone. A server would classify or allowlist intent, serve clinic facts from trusted structured data, filter model output, cap conversation history, add moderation and escalation rules, and log incidents. The model should not directly access sensitive tools or records.

20. Why is chat history stored only in React state?

It keeps the MVP simple and privacy-conscious: the chat disappears on a page refresh and is not persisted in the application. If persistence were needed, I would first define consent, retention, encryption, access-control, and healthcare compliance requirements.

5. Styling, UX, performance, and deployment

UX21. Why use Tailwind CSS?

Tailwind provides fast, responsive, utility-first styling while the configuration extends the brand colours and fonts. Shared component classes in the global CSS capture frequently reused patterns. This gives design consistency without maintaining a large custom stylesheet.

22. How are animations implemented responsibly?

Framer Motion powers page transitions, reveal animations, menus, carousels, and the chat widget. Animation is used to clarify navigation and interaction rather than block access to content. The home page also imports reduced-motion support, which is important for motion-sensitive users.

23. What accessibility work is visible in the project?

The app includes semantic buttons and links, labels and input types for form controls, alt text for images, descriptive ARIA labels for toggles, and aria-expanded on the mobile menu. The next improvement would be a full keyboard and screen-reader audit, including focus trapping in the chat and contrast checks.

24. How does the project support SEO?

The base document includes title, meta description, canonical URL, Open Graph metadata, favicon, and mobile viewport tags. App.jsx updates the document title per route. Because it is a pure SPA, server-rendering or pre-rendering would improve crawlability for route-specific metadata and initial content.

25. What performance improvements would you make first?

I would use route-level code splitting with React.lazy, lazy-load the chat widget and below-the-fold images, optimize and serve responsive image formats such as WebP/AVIF, assess animation cost on low-end phones, and run Lighthouse. The global AI component is a good candidate for deferred loading.

26. Explain the SPA deployment rule in public/_redirects.

A direct request to a client-side URL such as /services would otherwise cause a static host to search for a physical file and return 404. The redirect rule returns index.html with status 200, then React Router renders the intended page in the browser.

27. How did you verify the project?

The production build command, npm run build, completes successfully. For a production release I would complement that with component tests, end-to-end tests for forms and routes, manual mobile checks, accessibility tests, and API failure-path testing.

6. Behavioural and ownership questions

28. What was the hardest design decision?

Keeping the solution simple while respecting healthcare risk. The project intentionally uses an appointment-request model instead of pretending to have real-time booking, and the AI assistant is restricted away from clinical diagnosis. I would frame this as choosing appropriate product boundaries for an MVP.

29. What would you do differently if given two more weeks?

I would build a small backend for secured AI access and appointment records, introduce live capacity or staff confirmation, add test coverage, run an accessibility pass, optimize assets and code splitting, and replace static content with an approved content-management workflow.

30. What did this project teach you?

It reinforced that frontend engineering is not only UI implementation. I had to model reusable data, handle asynchronous integrations, validate user inputs, create mobile-friendly interactions, account for deployment routing, and think critically about privacy and safety in a healthcare context.

Rapid-fire revision

  • React Router: maps URL paths to React components without full page reloads.
  • Vite: fast frontend development server and production bundler.
  • Tailwind: utility-first CSS framework configured for the clinic brand.
  • Framer Motion: declarative React animation library.
  • useState: local mutable component state.
  • useEffect: synchronization with browser APIs, events, timers, and external effects.
  • localStorage: persistent browser key/value storage; used for theme preference.
  • sessionStorage: browser-tab/session storage; used for one-time chat intro behaviour.
  • Environment variables: build-time configuration; frontend variables must not contain secrets.
  • Client validation: UX support, not a security boundary.
